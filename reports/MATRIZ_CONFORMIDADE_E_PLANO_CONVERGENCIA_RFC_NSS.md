# Matriz de conformidade e plano de convergência do NSS

**Preparado em:** 2026-11-22; atualização de evidência em 2026-11-22

**Objetivo:** inventariar a conformidade observável do NSS com o RFC-NSS-001 v1.5 e com as regras locais dos repositórios, registrar evidências e definir o caminho de convergência.
**Limite:** auditoria documental e dos checkouts locais. Status `VALIDADO` abaixo significa que a evidência indicada cobre o critério específico; não certifica produção, requisitos institucionais ou requisitos mais amplos agrupados na mesma linha.

## Escopo revisado aprovado — fase `nss-v1`

Para esta fase pré-publicação, todos os testes de integração, E2E e deployment devem usar o projeto descartável `nss-v1`. É permitido apagar e recriar apenas os dados/volumes desse ambiente e aplicar diretamente o schema atual. Não é necessário garantir compatibilidade com cada commit anterior nem executar migrations de upgrade: não há primeira versão publicada com backend.

O critério de aceite é o snapshot atual funcionar de forma coerente e segura, preservando autenticação, autorização, tokens, permissões, integridade, contratos e limites de confiança. O ambiente ativo não deve ser alterado. Migrations e compatibilidade de upgrade ficam para quando houver necessidade de produção.

DT-10, DT-11 e DT-13 ficam deliberadamente por último, após a convergência técnica e a definição de marca/conteúdo. Smoke tests podem usar um recorte pequeno, como Raiva e um ano com poucos casos, sem substituir a validação epidemiológica já existente.

## 1. Como ler esta matriz

### Status

| Status | Significado |
|---|---|
| **VALIDADO** | Evidência executada/observável cobre o critério delimitado na linha. |
| **PARCIAL** | Há implementação ou validação, mas faltam partes do requisito ou sua verificação atual. |
| **DIVERGENTE** | O comportamento observado difere do requisito, ou interface/API/schema não concordam. |
| **AUSENTE** | Não foi encontrada implementação no escopo inspecionado. |
| **BLOQUEADO** | Depende de decisão, destinatário, autoridade institucional ou ambiente externo. |
| **NÃO VERIFICADO** | A evidência disponível não permite concluir. |
| **N/A** | Requisito não se aplica ao modo de implantação/escopo da validação, com justificativa. |

Frontend e backend são avaliados separadamente quando o requisito envolve ambos. Código presente não equivale a comportamento validado. Os estados `VALIDADO` e `PARCIAL` são limitados à evidência citada e ao snapshot nela registrado.

### Regra de reconciliação

O RFC é a linha de base de requisitos, mas não é um oráculo cego para a implementação. Se o código implementa proteção mais forte ou comportamento mais completo que o RFC, isso será registrado como **CONVERGENTE COM MELHORIA**, preservando o comportamento e documentando a razão. Divergências serão confrontadas também com contratos versionados, decisões aprovadas, invariantes de segurança/dados e uso real. Nenhuma regressão será recomendada apenas para fazer o código coincidir literalmente com texto antigo. Ambiguidade sem decisão registrada vira **RECONCILIAÇÃO NECESSÁRIA**, não uma escolha tácita do implementador.
